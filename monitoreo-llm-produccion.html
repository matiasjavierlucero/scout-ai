El directorio evals/ — sistema de evaluación automática

💡
¿Son obligatorios para correr la app?
No. La app funciona completamente sin ellos. Los evals no se ejecutan en runtime — son una herramienta de desarrollo, como los tests unitarios. Corren antes de deployar, no durante el uso normal. Si nunca los corrés, Scout AI funciona igual.
Lo que perdés sin evals: no sabés si un cambio en el código empeoró la calidad de las respuestas hasta que alguien se queja.
golden_set.py
10 queries con ground truth
4 RAG · 3 Stats · 3 Comp
Cada query tiene: agentes esperados, keywords obligatorias, jugadores que deben aparecer, timeout máximo.
Escrito a mano — es la fuente de verdad.
sanity.py
7 checks determinísticos
Sin LLM · microsegundos · 100% reproducibles.
¿Tiene contenido? ¿Agentes correctos? ¿Keywords presentes? ¿Stats en rango? ¿Respondió a tiempo?
Primera línea de defensa.
llm_judge.py
LLM como juez de calidad
Evalúa relevancia, grounding y coherencia.
Lento · opcional · activar con --judge.
Con GROQ_API_KEY: juez independiente (gpt-oss-120b) → scores confiables.
Sin key: cae a Ollama → mismo modelo → bias activo.
run_evals.py
CLI + CI gate
Corre los 10 casos, imprime el resumen, envía scores a Langfuse.
Exit code 0 si pasa · Exit code 1 si falla.
Integrable en GitHub Actions / CI.
Cómo correr los evals
Solo sanity checks (rápido, sin LLM)
uv run python evals/run_evals.py
Con LLM-as-judge (lento, scores orientativos)
uv run python evals/run_evals.py --judge
Un solo caso para debug rápido
uv run python evals/run_evals.py --case stats-001
Threshold personalizado (default: 0.7)
uv run python evals/run_evals.py --threshold 0.85
Pipeline completo de una corrida de evals
golden_set
Carga los 10 casos
Cada caso tiene la query, lo que se espera y el timeout máximo. Ground truth manual — no cambia automáticamente.
graph.run()
Ejecuta cada query contra el sistema real
Invoca el mismo run() que usa la app. No hay mocks — es el sistema de producción.
sanity.py
7 checks rule-based sobre el InformeScouting
has_content · agentes_correctos · keywords_presentes · jugadores_mencionados · stats_en_rango · schema_completo · response_time. Cada check devuelve un score 0.0–1.0.
llm_judge
Evaluación LLM — solo con --judge
Si no se activa la flag, este paso se salta completamente. No afecta el score final ni el exit code.
Langfuse
Envía scores por caso + promedio global
Si no hay keys configuradas, se loguea un mensaje y sigue. Nunca rompe el script.
exit code
Score promedio ≥ threshold → exit 0  ·  Score < threshold → exit 1
El threshold default es 0.7. Exit code 1 bloquea un deploy en GitHub Actions si el workflow lo chequea.

CI/CD — GitHub Actions como gate de calidad

🔁
¿Qué hace el workflow y cuándo corre?
El archivo .github/workflows/evals.yml define un job que corre automáticamente en cada push a master y en cada Pull Request. Su objetivo: garantizar que ningún cambio de código rompa la calidad de las respuestas del sistema. Si el score promedio cae debajo del threshold, el commit queda marcado como fallido y el PR no puede mergearse hasta que se corrija.
Pasos del workflow — en orden
checkout
actions/checkout@v4
Clona el repositorio en el runner. Incluye los archivos data/ que están commiteados — sin esto el agente no puede arrancar.
uv
astral-sh/setup-uv@v4 + uv sync
Instala uv (el package manager del proyecto) y resuelve todas las dependencias desde uv.lock. Equivalente a pip install -r requirements.txt pero reproducible y fast.
HF cache
actions/cache@v4 — modelo de embeddings
El modelo paraphrase-multilingual-MiniLM-L12-v2 pesa ~470 MB. Sin cache, se descarga en cada corrida (~2 min extra). Con cache, la primera corrida lo baja y las siguientes lo reusan desde ~/.cache/huggingface.
evals
uv run python evals/run_evals.py --threshold 0.7
Exit 0 → check verde, el PR puede mergearse. Exit 1 → check rojo, GitHub bloquea el merge hasta que alguien corrija el problema y vuelva a pasar.
4 secrets que necesitás configurar
GROQ_API_KEY Para que el juez LLM use gpt-oss-120b independiente
LANGFUSE_PUBLIC_KEY Para enviar scores de evals al dashboard
LANGFUSE_SECRET_KEY Para enviar scores de evals al dashboard
LANGFUSE_BASE_URL Si usás self-hosted; omitir para cloud.langfuse.com
Los secrets se configuran en GitHub → Settings → Secrets and variables → Actions. El workflow los inyecta como variables de entorno solo durante la ejecución — nunca quedan en logs.
Qué pasa si no configurás los secrets
Sin GROQ_API_KEY
El juez LLM no corre. Los sanity checks siguen funcionando. El score se calcula solo con checks determinísticos — igual de válido para CI.
Sin keys de Langfuse
Los scores no se envían al dashboard. El workflow sigue corriendo y el exit code sigue siendo correcto. Langfuse es opcional en CI.
Sin ningún secret
El workflow corre completamente offline — solo sanity checks, sin reportar. Es válido como gate básico de regresión.

El directorio scout/ — el núcleo del sistema

🧠
Cada archivo tiene una responsabilidad única y clara
Los archivos tienen una cadena de dependencias: schemas → llm → tools → agents → graph. Los últimos tres son el corazón — tools tiene los datos, agents coordina el uso de tools, graph coordina los agents. tracing.py y viz.py son ortogonales: se enchufan sin modificar la lógica central.
schemas.py
Contrato de salida
Define InformeScouting — el modelo Pydantic que devuelve el sistema
Tiene 8 campos: la query original, qué agentes corrieron, el texto de cada agente (RAG/stats/comp), la conclusión, y las listas de jugadores detectados. Los campos de agentes no ejecutados quedan como string vacío — nunca hay None. Este schema es el único punto donde el sistema define su API pública.
llm.py
Factory de LLM
Una función make_llm() que elige el provider según las env vars
Prioridad en orden: LiteLLM → Groq → Ollama.
LITELLM_MODEL=groq/llama-3.1-8b-instant → Groq gratis en producción.
Sin env vars → Ollama local en localhost:11434. El código de agents y graph nunca sabe qué provider está corriendo.
tools.py
Capa de datos
4 tools — la única capa que toca los datos reales
buscar_jugadores(query) — RAG: embedding de la query + similitud coseno contra los 1885 vectores. Devuelve los k más similares.
stats_jugador(nombre) — lookup fuzzy en el CSV, devuelve stats /90 con advertencia si <450 min.
comparar_jugadores(a, b) — tabla lado a lado con marcador al mejor en cada métrica.
buscar_por_nombre(nombre) — hasta 5 candidatos para que el agente resuelva ambigüedad antes de pedir stats.
agents.py
3 agentes ReAct
Cada agente es un create_react_agent con sus tools específicas
RAG agent → solo tiene buscar_jugadores. Responde queries de perfil.
Stats agent → tiene buscar_por_nombre + stats_jugador. Resuelve ambigüedad antes de buscar stats.
Comp agent → tiene buscar_por_nombre + comparar_jugadores.
Fix crítico: el output del agente se extrae del ToolMessage, no del texto final del LLM — porque llama3.2:3b parafrasea y a veces inventa.
graph.py
El orquestador
El StateGraph de LangGraph que conecta todo
orchestrator_node: heurísticas en <1ms para decidir qué agentes invocar.
route_to_agents: edge condicional que devuelve Send objects — activa agentes en paralelo.
synthesis_node: fan-in, construye el InformeScouting con los resultados.
run(): función pública que acepta callbacks para Langfuse y retorna el informe.
tracing.py
Observabilidad
Singleton de Langfuse + factory del CallbackHandler
get_langfuse() retorna el cliente o None si no hay keys — nunca rompe el flujo.
get_callback_handler() crea una instancia nueva por query — cada query genera un trace independiente.
Acepta LANGFUSE_BASE_URL o LANGFUSE_HOST para US/EU region.
viz.py
Visualizaciones
Figuras Plotly para el dashboard — no tiene lógica de negocio
build_radar(data_a, data_b?) — radar de percentiles de un jugador o superpuesto para dos. Los percentiles se calculan contra el dataset completo de 1885 jugadores.
build_pitch(position) — campo de fútbol con la zona de la posición resaltada.
get_player_data(name) — lookup en el CSV para enriquecer los cards del dashboard.

Observabilidad — cómo leer el dashboard de Langfuse

🔭
¿Qué problema resuelve tener observabilidad?
Sin observabilidad, cuando una respuesta es mala la única pregunta que podés responder es "¿qué devolvió el sistema?". Con Langfuse podés responder: ¿qué hizo exactamente cada agente, cuánto tardó cada paso, qué le pasó al LLM, y qué devolvió cada tool? La diferencia es la distancia entre un sistema que "parece funcionar" y uno del que sos responsable en producción.
Anatomía de un trace — tipos reales que muestra Langfuse
Verificado contra un trace real. Los tipos aparecen como íconos y etiquetas en la columna Type de la tabla.
AGENT span raíz o el LLM del agente ReAct
CHAIN nodos de LangGraph (orchestrator, rag_node, synthesis…)
GENERATION llamada real al modelo (input/output tokens, latencia del LLM)
TOOL ejecución de una tool (0 tokens, siempre <1ms)
AGENT scout-query latencia total de la query completa
├── CHAIN LangGraph wrapper del graph completo
├── CHAIN orchestrator <1ms · 0 tokens · output: routing flags
├── CHAIN route_to_agents Send API — decide qué nodos activar
├── CHAIN rag_node agente RAG completo (ReAct loop)
├── CHAIN LangGraph mini-graph interno del create_react_agent
│  ├── AGENT ChatOllama decide qué tool llamar
│  │ └── GENERATION model tokens de entrada + salida · latencia real del LLM
│  ├── CHAIN tools wrapper de ejecución de tools
│  └── TOOL buscar_jugadores("mediocampista ofensivo…") 0.3s · 0 tokens · similitud coseno
└── CHAIN synthesis construye InformeScouting · sin LLM
└── AGENT ChatOllama stream_conclusion — conclusión en streaming
💡 GENERATION es el único span con costo real: es la llamada directa al modelo — ahí ves input tokens, output tokens y latencia del LLM. Un CHAIN o AGENT que lo envuelve incluye ese tiempo más overhead de LangGraph, que es insignificante.
💡 TOOL siempre es <1ms y 0 tokens: es código Python puro (lookup en DataFrame o similitud coseno en NumPy). Si ves una TOOL lenta, el problema es de I/O o de datos, no del LLM.
Latencia
Total: cuánto tardó la query entera.
Por agente: qué nodo fue el cuello de botella.
Tool vs LLM: si el LLM es lento, el provider tiene latencia alta. Si la tool es lenta, hay un problema de datos.
Tokens y costo
Input tokens: contexto + historial + tool results.
Output tokens: respuesta del LLM.
Langfuse calcula el costo por query según el modelo — útil para presupuestar antes de escalar.
Sessions
En la vista Sessions de Langfuse se pueden agrupar traces de una misma conversación usando un session_id. Actualmente cada query genera un trace independiente — agruparlos por sesión es una mejora futura de observabilidad.
Scores de evals
Cuando corrés run_evals.py, los scores de sanity y judge se envían a Langfuse con el eval_run_id. En la pestaña Scores del dashboard podés ver la evolución del score promedio entre corridas.

Prompt Management — prompts versionados en Langfuse

✏️
¿Por qué gestionar prompts fuera del código?
Un prompt es la especificación de comportamiento de un agente. Cambiar un prompt sin Langfuse implica: editar el código → commit → push → deploy → esperar. Con Langfuse Prompt Management: abrís el dashboard → editás el texto → guardás → el cambio aplica en el próximo request. Sin tocar código. Sin deploy. Y con historial de versiones y rollback con un click si algo empeora.
Cómo funciona el flujo completo
setup_prompts.py
Una sola vez — sube los prompts iniciales a Langfuse
Crea los 3 prompts (scout-rag-agent, scout-stats-agent, scout-comp-agent) con el label production. Después de este paso, los prompts viven en Langfuse — el código solo es fallback.
Langfuse dashboard
Donde editás los prompts → Prompt Management
Cada edición crea una nueva versión numerada. Podés ver el diff entre versiones, dejarlas en borrador, promoverlas a production, o hacer rollback a cualquier versión anterior. Sin tocar código.
prompts.py
Fetches el prompt de Langfuse en cada arranque
Llama a langfuse.get_prompt(name, label="production"). Si Langfuse no está disponible o la key no existe, cae automáticamente al texto hardcodeado en el mismo archivo. El sistema nunca falla por un prompt faltante.
agents.py
Usa get_prompt() al inicializar cada agente
system_prompt=get_prompt("scout-rag-agent") — el agente recibe el texto final, sin saber si vino de Langfuse o del fallback. Cambia el prompt en Langfuse → reiniciás la app → el agente usa la nueva versión.
Para usar por primera vez
Subir los 3 prompts a Langfuse (una vez)
uv run python scripts/setup_prompts.py
Después del primer setup_prompts.py, los prompts aparecen en el dashboard bajo Prompt Management con la etiqueta production. No hay que volver a correrlo.
Qué podés hacer desde el dashboard
Editar el texto del prompt directamente (nueva versión numerada automática)
Comparar versiones lado a lado (diff visual)
Rollback a cualquier versión anterior con un click
Dejar versiones en borrador sin afectar producción
Ver en qué traces se usó cada versión del prompt

Preguntas de entrevista — con respuestas preparadas

Arquitectura ¿Por qué usaste LangGraph y no construiste el loop de agentes manualmente? ▶

LangGraph te da resuelto lo que tardarías días en reimplementar bien:

El ReAct loop (razonar → actuar → observar), la propagación automática de callbacks de observabilidad a todos los nodos, el paralelismo con la Send API, y la gestión de estado compartido con type-checking.

Si implementás el loop manualmente, empezás bien y a los tres días estás peleando con el estado entre agentes, los errores silenciosos y el debug. LangGraph tiene ese battle-testing hecho.

💡 Dato clave: el proyecto anterior incluía implementar el ReAct loop a mano. LangGraph es exactamente eso, pero production-ready.

Arquitectura ¿Cómo funciona el routing del orquestador? ¿Por qué no usás un LLM para decidir qué agentes invocar? ▶

El orquestador usa heurísticas determinísticas en <1ms:

1. Busca keywords de comparación ("compará", "vs", "diferencia") → activa el agente Comp
2. Detecta tokens que coinciden con nombres del índice de 1885 jugadores → activa Stats
3. Si no encontró nada específico → búsqueda semántica por perfil (RAG)

Usar un LLM para el routing agregaría 1-3 segundos de latencia en TODAS las queries, con no-determinismo incluido. Las heurísticas son predecibles y cuando fallan es fácil corregirlas.

💡 Principio en juego: si algo se puede resolver con código determinístico, no gastes tokens de LLM en eso.

Arquitectura ¿Qué es la Send API de LangGraph y por qué la usás? ▶

La Send API permite que un nodo dispare mensajes a múltiples nodos al mismo tiempo. LangGraph los ejecuta en paralelo y el nodo synthesis espera a que todos terminen (patrón fan-out → fan-in).

Sin Send API (secuencial): RAG (8s) + Stats (8s) + Comp (8s) = 24 segundos
Con Send API (paralelo): max(RAG, Stats, Comp) = ~8 segundos

Cada agente es completamente independiente — no depende del resultado del anterior — así que el paralelismo es seguro. El estado compartido usa operator.add para que cada agente escriba sus resultados sin pisar al otro.

Arquitectura ¿Por qué no usás MemorySaver para el contexto multi-turno? ▶

Decisión contraintuitiva que vale la pena entender bien.

MemorySaver persiste el estado entre invocaciones usando operator.add, que acumula listas. Si en el turno 1 el agente Comp devolvió una comparativa, en el turno 2 ese resultado sigue en el estado — y el nodo synthesis lo incluye en el informe aunque el usuario no haya pedido una comparación.

El contexto multi-turno se maneja explícitamente: la app guarda los jugadores del turno anterior en session_state de Streamlit y los pasa como parámetros limpios en cada nueva invocación del graph. Cada run empieza con estado vacío.

Esto da control total sobre qué se recuerda y qué no, sin efectos secundarios del estado acumulado.

LLM / Agentes ¿Qué es un agente ReAct y cómo funciona dentro de LangGraph? ▶

ReAct es un patrón donde el LLM alterna entre Razonar y Actuar hasta que tiene suficiente información para responder:

1. El LLM recibe la query y decide qué herramienta (tool) llamar
2. La tool se ejecuta y devuelve el resultado
3. El LLM procesa el resultado y decide si necesita más info o puede responder
4. Se repite hasta que decide que tiene suficiente

En LangGraph, create_react_agent compila este loop como un mini-graph. Cada uno de los tres agentes (RAG, Stats, Comp) es uno de estos mini-graphs que corre dentro del graph principal.

💡 Problema con llama3.2:3b: parafrasea el output de las tools y a veces inventa datos al hacerlo. El fix: se extrae el ToolMessage directamente de la conversación, saltando el texto final del LLM.

LLM / Agentes ¿Cómo garantizás que el agente no invente estadísticas (hallucinations)? ▶

Tres mecanismos en capas:

1. Bypass del LLM para los datos: el resultado de la tool se toma directamente del ToolMessage, no del texto final que generó el LLM. Lo que el LLM "dice" sobre el resultado es irrelevante — usamos el dato crudo de la tool.

2. System prompt restrictivo: "Siempre mostrá los resultados de la tool directamente, sin inventar información adicional".

3. Sanity checks en evals: validamos que los valores numéricos estén en rangos físicamente posibles (xG/90 entre 0 y 2, pases/90 entre 0 y 150, etc.).

El principio: el LLM es el coordinador, no la fuente de verdad. Los datos vienen del CSV. El LLM solo decide cuándo y cómo presentarlos.

LLM / Agentes ¿Qué problema resuelve LiteLLM y cómo está implementado? ▶

Sin LiteLLM, cambiar de Ollama (dev local) a Claude (producción) requiere cambiar código: distintas clases, distintos parámetros, distintas API keys hardcodeadas.

LiteLLM unifica todos los providers bajo una única interfaz. El modelo se especifica con un string con prefijo de provider:

LITELLM_MODEL=ollama/llama3.2:3b → Ollama local (dev)
LITELLM_MODEL=groq/llama-3.1-8b-instant → Groq (staging, gratis)
LITELLM_MODEL=claude-sonnet-4-6 → Claude (producción)

El código del agente no cambia. Solo cambia una variable de entorno. Eso es lo que querés en producción: configuración separada del código.

Datos ¿Qué es RAG y cómo está implementado en Scout AI? ▶

RAG (Retrieval-Augmented Generation) es recuperar información relevante de una base de datos antes de generar la respuesta, en vez de que el LLM intente inventar o recordar los datos.

Paso offline (una sola vez): generamos un perfil textual para cada jugador ("Lionel Messi: Forward, 2000 min, xG/90: 0.55, pases/90: 67…"). Convertimos ese texto a un vector de 384 números con sentence-transformers y lo guardamos en disco.

Paso runtime (por query): la query del usuario ("mediocentro defensivo que recupere balones") se convierte al mismo espacio vectorial. Calculamos similitud coseno contra los 1885 vectores y devolvemos los k más cercanos.

Esto permite encontrar jugadores por perfil de juego en lenguaje natural, no solo por nombre exacto.

Datos ¿Por qué embeddings multilingüe? ¿Por qué ese modelo en particular? ▶

Hay dos idiomas en juego: los perfiles de jugadores están en inglés (posiciones en StatsBomb: "Right Center Midfielder", etc.), pero los usuarios escriben en español.

Un modelo monolingüe (inglés) no entendería que "mediocampista" y "midfielder" son lo mismo. El modelo paraphrase-multilingual-MiniLM-L12-v2 fue entrenado en 50+ idiomas y mapea esos conceptos al mismo lugar en el espacio vectorial.

¿Por qué MiniLM y no algo más grande? Tradeoff consciente: corre en CPU en ~1 segundo, tiene 384 dimensiones (suficiente para este dominio) y es multilingüe. Un modelo más grande sería marginalmente mejor pero incompatible con el objetivo de correr todo localmente sin GPU.

Datos ¿Por qué normalizás las estadísticas a "por 90 minutos"? ▶

Sin normalización, un jugador que jugó 3000 minutos tendría en total muchos más goles y pases que uno que jugó 500 minutos, aunque el segundo sea claramente mejor.

Dividir por minutos jugados × 90 convierte los totales en tasas por partido completo. Esto hace comparables a jugadores con volúmenes de juego muy distintos: un titular de toda la temporada vs uno que vino del banco.

El sistema también advierte cuando un jugador tiene menos de 450 minutos (menos de 5 partidos). Con tan poca data, un buen partido puede inflar los números artificialmente. Se muestra la advertencia pero no se filtra: esa decisión la toma el scout, no el sistema.

Producción ¿Qué problema resuelve Langfuse en producción y cómo está integrado? ▶

Sin observabilidad, cuando algo falla no podés responder "¿qué hizo exactamente el sistema?". En un banco esto no es opcional — es compliance.

Langfuse graba por cada query:

• Cuánto tardó cada agente (RAG, Stats, Comp, conclusión)
• Qué tokens usó y cuánto costó
• Qué tool llamó el agente y qué devolvió
• El trace completo con todos los mensajes

Integración minimal: un CallbackHandler se pasa como config={"callbacks": [handler]} al graph.invoke(). LangGraph propaga ese callback automáticamente a todos los nodos y agentes internos — sin tocar el código de los agentes. Un punto de instrumentación, cobertura total.

Producción ¿Qué pasa cuando el usuario escribe un nombre incompleto o un apodo? ▶

Las tools usan fuzzy matching con el algoritmo Ratcliff/Obershelp: calcula la proporción de caracteres en común entre strings.

"Busquets" → encuentra "Sergio Busquets Burgos" ✓ (alta similitud)
"Messi" → encuentra "Lionel Andrés Messi Cuccittini" ✓
"Xavi" → NO encuentra "Xavier Hernández Creus" ✗ (no comparten tokens)

Limitación conocida y documentada: los apodos que no comparten caracteres con el nombre oficial no funcionan. El fuzzy opera sobre texto, no sobre conocimiento semántico.

La herramienta buscar_por_nombre devuelve hasta 5 candidatos para que el usuario confirme — en vez de asumir un match silencioso que podría ser incorrecto.

Evals ¿Qué son los evals y por qué son importantes en un sistema de IA en producción? ▶

Los evals son tests automáticos de calidad que miden si el sistema responde bien — el equivalente a los unit tests, pero para el comportamiento del LLM.

En Scout AI hay dos capas:

Sanity checks (rule-based, sin LLM): ¿el informe tiene contenido? ¿corrieron los agentes correctos? ¿los valores numéricos están en rango posible? ¿respondió en menos de N segundos? Son determinísticos y baratos — siempre corren.

LLM-as-judge: un modelo evalúa relevancia, grounding y calidad. Más lento — se activa explícitamente con una flag.

Los evals permiten: detectar regresiones cuando cambiás el código, comparar versiones objetivamente, y bloquear un deploy si el score cae por debajo de un threshold. El script termina con código 1 si falla — integrable directo en CI/CD.

Evals ¿Por qué el LLM-as-judge con el mismo modelo es una mala práctica? ▶
⚠️ Este es el red flag más importante del sistema — el entrevistador probablemente lo va a preguntar.

Se llama self-serving bias: un modelo tiende a calificar bien sus propias respuestas independientemente de la calidad real. Es como pedirle a un alumno que se califique a sí mismo — siempre tenderá a darse una nota alta.

Por qué pasa: el modelo aprendió a generar texto que "suena coherente" para su propio estilo. Cuando evalúa ese texto, lo reconoce como coherente y lo califica alto, aunque la respuesta sea incorrecta o irrelevante.

En producción el juez DEBE ser un modelo independiente y más capaz: Claude Sonnet, GPT-4o, o al menos una familia diferente con más parámetros. Más capaz porque el juez tiene que detectar errores que el agente mismo cometería.

Acá usamos el mismo modelo solo para aprender el patrón del pipeline de evals. Los scores no son válidos para decisiones de deploy. Esto está documentado explícitamente en el código.
